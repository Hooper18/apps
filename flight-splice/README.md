# flight-splice：自拼中转最低价路线搜索

起因：杭州→冰岛直搜 1w+，但杭州→罗马 2k+ 加 罗马→冰岛 <1k。机票按
「出发地-目的地市场」定价而非距离，把两个竞争激烈的市场手动拼起来，
远便宜于一个无竞争市场的联程票——本工具把这件事自动化：给定 A→B 和
出发时间窗，枚举经欧洲/中东候选枢纽的两段自拼组合，输出比直搜省多少。

## 技术路线（2026-07 实测结论）

- **个人拿不到中立实时运价接口**：Kiwi Tequila 已转邀请制（Travelpayouts
  渠道要 5 万 MAU）；Amadeus Self-Service 不含低成本航司（自拼便宜段恰恰
  靠 LCC）；Skyscanner 仅合作伙伴；携程/飞猪要企业资质。
- **数据源 = Google Flights 真浏览器渲染**：本机出口 IP 下 Google 不做
  服务端直出（`ds:1` payload 里航班列表为 None），裸 HTTP（fast-flights
  默认通道）拿不到数据；用 Playwright 无头 Chromium 渲染后从结果行的
  aria-label 解析（英文锁定 `hl=en`，含价格/经停/航司/起降时刻/时长）。
- **三阶段控制请求量**（默认约 150 次浏览器查询，全程磁盘缓存可断点续跑）：
  1. 直搜基准：窗口内每天 A→B 单一客票最低价（对照组）
  2. 枢纽海选：窗口中点日期给每个枢纽查两段，按两段最低价之和排枢纽
  3. 入围精查：Top-K 枢纽拉全窗口两段矩阵 → 组合 → 过滤 → 排序
- **自拼票价可加**（每段独立客票），无联程运价的历史依赖问题，组合层
  = 逐枢纽笛卡尔积 + 转机时间硬约束（默认 ≥5h、≤48h），再做同
  (段1日期, 段2日期) 去重（每对只留最便宜代表）并按 top-per-hub 截断。
- Travelpayouts 缓存矩阵客户端（`splice/travelpayouts.py`，48h 用户搜索
  缓存）已实现但**尚未接入 CLI 管线**，属待办加速器；当前粗筛精筛
  全部走 Google 实时渲染。

## 用法

```powershell
.venv\Scripts\python.exe -m splice.cli --from HGH --to KEF --start 2026-09-07 --days 7
```

常用参数：`--min-connect 5`（最小衔接小时）、`--shortlist 6`（入围枢纽数）、
`--all-visa`（纳入英国/土耳其等需额外签证的枢纽）、`--top 10`。
报告输出到终端并存 `results/`。

## 候选枢纽与签证（中国普通护照）

自拼必须入境中转国（取行李重新值机），签证是硬约束，`splice/hubs.py`
按类别标注：申根（去冰岛顺路零成本）/ 免签（阿联酋、卡塔尔）/ 需额外
签证（默认排除，`--all-visa` 纳入）。

## 风险模型（工具输出里逐条标注）

自拼 = 分开出票：误机无航司保护（衔接宁长勿短）、行李需重挂（轻装优先）、
过夜中转要算住宿成本。价格为查询时点报价，出票前以航司/OTA 实时价为准。

## 测试

```powershell
.venv\Scripts\python.exe -m pytest -q
```

纯逻辑（aria 解析 / 组合过滤 / TP 映射）全部离线可测；`sanity_live.py`
是单查询实连自检（验证渲染→解析→缓存全链路）。

## 已知边界

- Google Flights 无官方 API，DOM/aria 结构变更会破解析——sanity 脚本
  是金丝雀；规模化或求稳可换 SerpApi（付费，`deep_search=true`）。
- 结果依赖出口 IP 的 Google 可达性（需科学上网）。
- 仅两段自拼；三段（两次自转）待做，收益预计有限但架构已留好口子
  （`build_splices` 输入就是逐枢纽的两段报价集合）。
